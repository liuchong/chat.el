# Stage — One chat surface (2026-08-26)

## What Prompted It

A question with no good answer: what is the difference between `chat` and
`chat-code`? Both opened a chat buffer, took typed input, streamed a
reply, ran tools and showed status. The honest answer was that each had
features the other should have had, in both directions, and that no
principle divided them.

It surfaced while planning transcript rendering. Writing that against two
renderers means writing it twice, and the second copy drifts from the
first — which is exactly how the two surfaces got into this state.

## What Changed

### The session model

`chat-code-session` is gone. Code capability is metadata on a plain
`chat-session`, reached through accessors generated by
`chat-code--define-property`, which also normalizes symbols and lists
back from their JSON round trip. Capability is therefore saved with the
session, restored when reopened, and visible in the ordinary session
list. `chat-code-from-chat` turns it on for the session in front of you
without restarting the conversation.

Branch creation was replacing the whole metadata alist, so a branch lost
the working directory and anything else the parent knew.
`chat-session-metadata-merge` now combines parent and override.

### The pipeline

For each duplicated pair, the better behaviour survived and the other was
deleted. From the code side: cutting a streaming update at a fence
boundary so a half-written block never renders as literal backticks;
summarizing a tool result by kind so a listing reads as file names and a
search as matches; asking for an output budget the provider will honour.
From the chat side: checking the buffer is alive before drawing, reading
project instruction files, both budgets.

1712 lines left `lisp/code/chat-code.el`; 475 arrived in
`lisp/ui/chat-ui.el`.

`chat-code-mode`, its keymap, its buffer setup and its header are gone.
`chat-code--open-session` calls `chat--open-chat-session`.
`chat-prepare-session-buffer` holds the setup both paths had drifted
apart on — the code path had lost working-directory restoration and
scratch setup.

### The keymap

One map. The two collided on `C-c C-a`: accept-edit against
auto-approval. Auto-approval moved to `C-c C-t`. Code keys are present in
every session and report plainly when a session lacks capability, rather
than being absent from the map.

### Obsolescence

`chat-code-use-streaming`, `chat-code-max-output-tokens`,
`chat-code-request-timeout`, `chat-code-tool-followup-timeout`,
`chat-code-tool-result-summary-max-chars` and
`chat-code-auto-path-completion` are aliases to their `chat-ui-`
equivalents. `chat-code-max-tokens`, `chat-code-history-max-tokens` and
`chat-code-request-safety-margin` are marked obsolete with what replaced
them, their meaning having not survived.

## What Went Wrong

A reachability pass keyed on the `chat-code` prefix reported three
helpers as dead: `chat-code--get-selection`,
`chat-code--get-function-at-point`, `chat-code--get-context-around-point`.
They are called from `chat-edit-*` commands in the same file, which the
prefix did not match. They were deleted and recovered from git.

`tools/dead-code-report.el` now blanks out the matched definitions and
treats any remaining mention in the file as a call, so everything that is
not a `chat-code` definition is a root too. It reports 35 defined, 35
reachable.

Two `defcustom`s were used above their definitions, which byte-compile
caught; they moved up.

Three modules outside `chat-code.el` still reached for the removed
buffer-local. `chat-tool-caller.el` read it to find the project root, so
file and shell tools silently lost the root for every coding session —
and five tests passed anyway, because they set that same variable rather
than the one the surface binds. They now bind `chat--current-session`,
and a new test asserts the negative the old ones could not: a session
without code capability must not widen the allowed directories, even when
it carries a project root in metadata.

`chat-code-git-add-to-context` was reading the removed variable too, so
it had quietly become a no-op, and it computed a formatted context it
threw away. It now reads capability from the session, unions rather than
appends, and no longer formats what it discards.
`chat-context-compact-current-session` was falling back to a deleted
helper; there is one place to look now.

## What Guards It Now

The keymap and `chat-commands-help` agree key by key in both directions.
The extraction is pinned to keys known to be documented, including
`C-c C-SPC`, whose shape reads as a prefix of itself and made an earlier
regexp report a key nobody had written. Comparison is on normalized
descriptions, since `C-c C-m` and `C-c RET` are the same key and
`S-RET` and `S-<return>` are the same key.

This is the check that would have caught the `C-c C-a` collision. Both
surfaces documented that key for their own command, so the conflict
existed in the help text before it existed in a merged keymap — and a
merged keymap cannot report it, because `define-key` overwrites in
silence.

`test-docs.el` requires every `M-x` name in the docs to be a command. It
found nine dead names: eight `chat-code-quote-*` and `chat-code-ask-*`
commands that had become `chat-quote-*` and `chat-ask-*` long before, in
both the cheatsheet and the README, plus a `chat-code-show-help` that no
longer existed. It also fails on any mention of `*chat:code:` or
`chat-code-mode` in user-facing docs. Both tests count what they checked,
so a regexp that stops matching fails rather than passes.

## Result

758 tests passing. Every file touched byte-compiles without new
warnings.
