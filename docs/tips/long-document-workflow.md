# 用 chat.el 写长文档的工作流

`chat.el` 已经可以拿来写文档。
更准确地说，它适合按 section 逐段起草和修改文档，而不是一次生成整本超长文本。

## 什么时候适合

- 写 `README`
- 写使用指南
- 写设计说明
- 写专题文章
- 补现有文档的一节或几段

## 什么时候不要一次做完

- 一本很长的 book-style 文档
- 超长单文件的一次性全文重写
- 需要把整份大文档完整塞进上下文再统一改写的场景

原因很简单：
- 单次输出预算有限
- 长对话会逐步做 summary
- 整文件引用到上下文有大小和行数边界

## 推荐工作流

1. 先确定文档层级。
2. 把任务拆成标题、小节、段落群。
3. 新文档先让 AI 起草一个 section。
4. 已有文档优先选中一个 heading 下的内容，再让 AI 改。
5. 每次只接受一个清晰块的修改。
6. 用 preview 和 `git diff` 审查后再继续下一块。

## 新文档怎么写

推荐方式：

1. 在 `docs/` 里先确定放置位置。
2. 用 `chat-code-start` 开一个会话。
3. 直接要求 AI 先写目录和第一节。
4. 对新文件使用 `files_write`。
5. 后续按节追加或重写，而不是一口气重做全文。

一个实用提示是，先让 AI 给出文档大纲，再逐节展开。
这样更容易控制风格和长度。

## 现有文档怎么改

优先顺序建议是：

1. `chat-code-quote-region`
2. `chat-code-quote-near-point`
3. `chat-code-quote-current-file`

如果只是修一节内容，优先选中那一节再提问。
如果当前文件不大，再考虑直接引用整个文件。

修改工具建议：

- 新文件或明确的整文件重写，用 `files_write`
- 精确文本替换，用 `files_replace`
- 多处局部修改，用 `apply_patch`

## 长文档的关键原则

- 一次处理一个 section
- 让 AI 改内容，不让 AI 替你做最终审稿
- 不把“超长输出”当默认交互方式
- 让 `git diff` 或 Magit 做最终观察面

## 常见失败方式

### 一次要求输出整篇超长文档

结果通常是：

- 输出被截断
- 后半部分质量下降
- 风格和结构不稳定

更稳的方式是先列提纲，再逐节展开。

### 直接引用超大文件

如果 `chat-code-quote-current-file` 拒绝，很可能是文件太大。
这时就改用 region 或当前标题块。

### 用整文件重写做小修改

这会让 diff 变大，也更难审查。
已有文档的小改动优先用 `apply_patch` 或 `files_replace`。

## 一个最小示例

1. 新建 `docs/articles/request-lifecycle.md`
2. 让 AI 先写标题、摘要、目录和第一节
3. 审稿并接受
4. 继续要求写第二节
5. 对第一节局部修改时，只引用第一节再改
6. 全部完成后统一用 `git diff` 审查

这比“一次把整篇都生成出来”稳定得多。
