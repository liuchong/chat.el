# 010: 运行中再次发送 Spec

## Overview

一次回答还没跑完,用户又按了回车。这件事目前有且只有一种处理方式,而它既没有被说明过,
也不是所有情况下都是对的。

现状是:输入被立刻写进会话,排进 `steering-queue`,在**下一个轮次开始前**被整队排空,
作为若干条独立的 `:user` 消息追加到本次 run 的消息列表里。用户会看到
"Message queued for the active response.",然后就没有别的反馈了。

这条路径本身没坏,但它把三个不同的意图压成了一个:

- **我想补一句,让你连着这次一起考虑** —— 插入是对的
- **我想让你先把这件事做完,再做下一件** —— 插入是错的,它把两件事搅在一轮里
- **算了,别做了,改做这个** —— 插入是最错的,模型会带着已经作废的任务继续跑

所以要三种,由用户选,而不是由实现替用户选。

另外两个已经确认存在的问题,和这三种模式无关但同属这条路径:

**多次输入没有结构。** 三条输入排空成三条 `:user` 消息,而 `chat-llm--format-one-message`
只把 `role` 和 `content` 送上线——消息结构体里的时间戳和 id 都不上线。模型看到的是三条
挨在一起的用户发言,分不清它们是同时来的还是依次来的、是补充还是改口、哪条最新。

**步数预算被稀释。** steering 不改 `max-steps`,而每个被 steering 撑起来的轮次照样
`(1+ step)`。所以插进来的输入是**花掉**预算而不是带来预算:第一句问题用掉六步,补的第二句
只剩两步可用。越是补在后面的、越可能是用户真正想要的那句,能用的余量越少。

## Current Status

施工前逐条核实过,不是推测:

**已经实现,不需要改**

- **上下文连续性。** 新一次 `/send` 的消息来自 `chat-session-messages`,经
  `chat-transcript-model-messages` 投影(只去掉纯展示类消息),再由
  `chat-ui--prepare-messages-with-tools` 前置系统提示。上一轮的 assistant 消息、
  它的 `tool_calls`、以及独立的 `:tool` 结果消息都在里面
  (`chat-llm--format-one-message` 分别编码 `role:"tool"` 与 `tool_calls`)。
  所以「一个 session 里的对话是连续生长的」这件事,现在就是成立的。
- **压缩是自动的。** `chat-context-auto-compact` 默认开,由每一步的
  `transform-context-fn` 调 `chat-context-prepare-messages` 触发,超过
  `chat-context-budget-compaction-limit` 就压。
- **压缩不会切坏工具配对。** `chat-context--compaction-plan` 用
  `chat-session-tool-pair-safe-cut-index` 选切点,不会把 `tool_calls` 和它的结果切开。

**与预期不符,必须说清**

- **「不可压缩区」保护的不是会话消息。** `chat-context-resident.el` /
  `chat-context-resident-partition` 保护的是**指令文件里的片段**——AGENTS.md 里标了
  `<!-- chat:resident -->` 的段落,使其免于指令文本的字符上限截断。
  `chat-context--compaction-plan` **完全没有调用 resident 的任何函数**。
  会话消息侧的保护只有两条:开头的 system 消息不切,工具配对不切。
  这两套机制名字相近、目标不同,之前被当成一回事了。本 spec 不改这件事,但把它记下来:
  「会话里某几条消息永不参与压缩」这个能力目前**不存在**,需要时应另起一份 spec。
- **打断会丢掉已经流出来的内容。** run 被 cancel 后,流式 sentinel 走
  `((chat-agent-run-state-cancelled run) nil)` 跳过 `chat-agent--handle-result`,
  UI 的 `agent-end` 在 `'cancelled` 分支只做清理、不调
  `chat-ui--finalize-response`。已经落过 `message-appended` 的完整步骤留在会话里,
  **本步流到一半的文本被丢弃**。这是 interrupt 模式必须先解决的前提。

## 命令形式

```
/send                      发出攒下的队列(现有行为,不变)
/send <消息>               用当前默认模式发送
/send <模式> <消息>        用指定模式发送这一条
/send <模式>               把该模式设为此后的默认
```

`<模式>` 是 `insert`、`queue`、`interrupt` 三者之一。

**模式词只在显式 `/send` 形式下解析。** 普通输入(不带命令前缀)走
`chat-ui--dispatch-plain-input`,和 `/send` 落到同一个 handler,所以如果两条路径都解析
模式词,直接打字说「queue 这个构建到明天」就会被吃掉第一个词、变成一条排队发送的
「这个构建到明天」。显式写了 `/send queue …` 是用户自己要的;直接打字不是。
想显式发一条以模式名开头的消息,写 `/send insert queue …`。

`/send <模式>` 单独一条设默认值,顺带解决了「模式名后面没有消息时该算什么」这个歧义:
它算一次设置,不算一条内容是模式名的消息。

**与 `/queue` 的区别必须在帮助里写明。** 已有的 `/queue` + `/flush` 是**发送前**把多条
笔记攒成一条消息;这里的 `queue` 模式是**发送后**等当前回答跑完再作为新命令发出。
两者同名不同事,而且都会保留。

## Requirements

### 1. insert(默认)

**1.1** 行为不变:输入立刻写进会话,排进 `steering-queue`,在下一轮开始前整队排空,
作为独立的 `:user` 消息追加进本次 run。

**1.2 多次输入必须结构化。** 排空时,每条注入的消息在上线内容前加一行标记,写明:
它是本批的第几条、共几条、到达时刻、以及它是在模型工作期间到达的。

```
[input 2 of 3 · 02:41:07 · arrived while you were working]
修一下这个
```

标记只加在**运行中注入**的消息上。正常发起一次对话的消息不加——它不需要解释自己是什么。

标记文本固定用英文,不随界面语言变。它是给模型看的协议标记,不是给用户看的文案;
本地化会让同一件事在不同用户那里长得不一样,而模型侧要的是稳定。

**1.3 新输入刷新剩余步数。** 每次 steering 入队时,把 `max-steps` 抬到
`当前 step + 配置的预算`,使最后一条输入也拿到完整预算。

不设总步数上限:每一次刷新都要求有人真的敲了一次回车,人本身就是这个循环的出口。
模型自己空转仍然受原预算约束,因为模型不会给自己 steering。

**1.4** 刷新与注入都要记进会话事件流(009 的 wire),`steering` 事件的 payload 已经记了
条数、message id 与 step,再加上刷新后的预算值。

### 2. queue

**2.1** 输入**不**进 `steering-queue`。它被挂在 UI 侧的待发列表上,当前 run 完全跑完
(`agent-end`,无论 status)之后,作为一次**新的** run 发出。

**2.2** 新 run 的上下文按现有路径从会话重建,所以上一次命令的结果自然在里面——
这一点不需要新代码,是 Current Status 里已核实的既有行为。

**2.3** 前一次 run 结束时状态为 `error` 或 `cancelled` 也照样发出排队的输入。
理由:排队的意图是「等这件事有个结果」,失败也是结果;吞掉用户的输入比带着一次失败
的上下文继续更糟。

**2.4** 排队期间用户可以看到有几条在等。多条排队按到达顺序依次成为独立的 run,
不合并——合并就是 insert,用户选了 queue 就是不想合并。

### 3. interrupt

**3.1** 输入**立即**打断当前 run。

**3.2 打断前必须把已经流出来的内容留下。** 本步流到一半的文本作为一条 assistant 消息
写进会话,并标明它是被打断的:

```
[interrupted after 1,204 characters]
```

否则「部分结果作为上下文一起用」这句话没有落点——现在这段文本在 cancel 之后就不存在了。

**3.3** 打断之后,用户的输入作为一次新的 run 发出。上下文里因此同时有:被打断那一步的
部分回答、它之前所有完成的步骤、以及新的输入。这正是用户要的「跟正常完成一样」。

**3.4** 没有内容可留(还没开始流)时,不写空消息,只打断。

### 4. 三种模式的共同约束

**4.1** 当前没有 run 在跑时,三种模式行为完全一致:立刻发起一次新 run。模式只在
「已经有东西在跑」时才有区别。

**4.2** 默认模式可配置(`chat-send-default-mode`),默认 `insert`——它是现状,
换默认值会改变所有现有用户的行为。

**4.3** 模式的选择要在界面上可见。用户看不到当前默认模式,就无法解释为什么同一个操作
这次插进去了、上次排了队。

## 非目标

- **不做「会话里某几条消息不参与压缩」。** 上面已说明,这个能力目前不存在,而且
  和本 spec 要解决的问题无关。需要时另起 spec。
- **不改 `/queue` + `/flush`。** 同名不同事,但它是既有行为,不在本次范围。
- **不做跨 run 的自动重试。** queue 模式在前一次失败后照发,但不重发失败的那一次。
- **不给 interrupt 做「撤销打断」。** 打断是用户明确要的动作,部分结果已经留在会话里,
  要接着做就再说一次。

## 验收

- `/send insert`、`/send queue`、`/send interrupt` 三条都能设默认,且设完之后界面上
  能看出当前是哪个
- 显式 `/send queue 修一下` 走 queue;直接打字 `queue 修一下` 走默认模式,且消息内容
  完整保留「queue」这个词
- insert:运行中连发三条,模型侧收到的三条消息各自带 `[input N of 3 · … · arrived
  while you were working]` 标记;正常发起的第一条不带标记
- insert:运行中在第 5 步注入一条,预算配置为 8 时 `max-steps` 变成 13,最后一条输入
  确实还有 8 步可用
- queue:运行中发一条,当前 run 跑完后它作为新 run 发出;前一次 run 被取消或报错时
  同样发出
- queue:运行中连发两条,得到两次独立的 run,顺序与到达顺序一致,不合并
- interrupt:流到一半时打断,会话里留下一条带 `[interrupted after N characters]`
  的 assistant 消息,内容是打断时已经流出的文本;紧接着的新请求的上下文里包含它
- interrupt:还没开始流就打断,不产生空的 assistant 消息
- 三种模式在没有 run 在跑时行为一致,由测试断言
