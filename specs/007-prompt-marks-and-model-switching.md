# 007: Prompt Marks And Model Switching Spec

## Overview

提示符要回答一个问题：**现在按回车会发生什么。**

今天它只回答了一半。`cmd> ` 说了哪个命令持有这一行，`> ` 说了没有命令持有它。
但"没有命令持有它"意味着这句话会发给某个模型，而**是哪个模型，提示符没说**。
状态行说了，可状态行在缓冲区顶部，光标在底部——这个距离已经因为同一个理由被
处理过一次：`chat-ui--input-prompt` 现有的注释写着，"一个长得像聊天框的 shell，
就是问题被当成命令执行的原因"。模型同理：一个长得像 Kimi 会话的窗口，就是问题
被发给别的厂商的原因。

这份 spec 做三件事：

1. 给能持有输入的每种模式一个可以扫一眼认出的标记
2. AI 模式下把厂商标记和模型名放到光标旁边
3. 配置了多个厂商时，让那一段可以点开切换

第三件事顺带解决一个真实的不便：换模型现在只有 `M-x chat-set-model` 一条路，而
用户看到模型名的地方和能改它的地方不是同一个地方。

## Non-Goals

- 不做模型的能力对比、价格、上下文长度展示。提示符是一行，不是面板。
- 不引入 `all-the-icons`、`nerd-icons` 或任何图标字体依赖。理由见 Requirement 1.3。
- 不改厂商注册接口。标记表按厂商符号查表，查不到有降级规则，注册接口不动。
- 不改 `> ` 这个结束符。它是既有习惯，换掉只会制造无谓的重新学习。

## Requirement 1: 模式标记

### 1.1 只有能持有输入的命令需要标记

`chat-ui--command-table` 里带 `:default sticky` 的命令才可能出现在提示符里：
`send`（基线，即 AI 模式）、`cmd`、`queue`。`:default reset` 的命令（`quick`、
`flush`）用完就回到基线，永远不会持有提示符，给它们设计标记是给不存在的状态
设计外观。

未来新增的 sticky 命令若没有标记，提示符退回今天的样子（只有命令名），不是错误。

### 1.2 字形不可显示时必须降级为纯文本

用 `char-displayable-p` 判定。一个显示成豆腐块的图标比没有图标更糟：豆腐块既
不传达信息，又占掉一个字符宽度，还让人以为程序坏了。

降级的结果必须仍然是可用的提示符，而不是缺了一块的提示符。

### 1.3 不用 emoji，用单色 BMP 符号

emoji 是双宽字符，依赖彩色字体，在等宽缓冲区里和周围文本对不齐；同一个码位在
不同平台上是不同的图形。单色 BMP 符号（Dingbats 区）宽度稳定、几乎所有等宽
字体都有、颜色由 face 控制而不是由字体控制——**颜色由 face 控制这一点是关键**，
因为品牌色必须能跟随明暗背景切换（Requirement 2.3）。

这条同时否掉图标字体方案：`nerd-icons` 需要用户装 Nerd Font，装了才好看，没装
就是豆腐块，而我们无法可靠检测"装了但字体不含这个码位"。

## Requirement 2: 厂商标记

### 2.1 AI 模式下厂商标记取代通用星标

有厂商就显示厂商的标记，没有（provider 查不到配置）才显示通用星标。两个都显示
是冗余的：它们说的是同一件事。

### 2.2 标记来源分两类

- **少数厂商的 logo 恰好有广泛可用的等价字符**，就用那个字符。这类是真的像，
  不是凑的：Claude 的星芒对应八角星号，Grok 对应乘号 X，OpenAI 的结对应
  八瓣星号，Gemini 的四角星对应白色四角星。
- **其余用显示名首字母大写。** 这不是偷懒，是有先例的做法——同平台的
  termini-desktop 对 Kimi 就是"K 跟随周围文本色，只有圆点用品牌色"。

首字母会撞（DeepSeek 和 Doubao 都是 D）。可以接受：紧邻的模型名区分它们，品牌色
也区分它们。为了避免撞而给厂商编造符号，代价更大。

### 2.3 品牌色只给已知的，且不得外借

只给确实有已知品牌色的厂商上色，其余继承周围文本色。**品牌色不得用于 chat.el
自己的界面元素**——用了就等于宣称那是我们的主题色，而它是别人的商标色。

品牌色必须提供明背景和暗背景两个值。一个在暗色主题上不可读的品牌色，比不上色差。

## Requirement 3: 模型名

### 3.1 显示的必须是这次请求真的会用的模型名

不是厂商显示名，不是 provider 符号，是 `(plist-get config :model)`——请求实际带
上去的那个字段。提示符只要显示一个不等于真相的名字，它就从"减少误发"变成了
"制造误发"。

### 3.2 过长的模型名截断，完整值放 `help-echo`

模型名可以到二三十个字符（`grok-4-fast-non-reasoning`）。截断宽度可配置，用
`string-width` 计算而不是 `length`，否则 CJK 名字会算错一半。

## Requirement 4: 点击切换

### 4.0 能选的必须是配置过的，而且要自动感知

**注册不等于可用。** chat.el 在加载时就把它会说的每一家都注册进 registry——
十六家——这跟这台机器有没有那家的账号毫无关系。`chat-llm-enabled-providers` 返回
的是注册过的那十六个，把它拿来当候选列表，等于把"这个包支持哪些厂商"的目录冒充
成"你可以选哪个"。

判据只有一个：**取不到 key 就是不可用。** registry 里没有任何别的字段能说明背后
有没有账号，而没有 key 的 provider 发请求必然失败。

必须是**每次显示时现算**，不是启动时算一次记下来：key 可能在会话中途才配好，
配好就该出现，删掉就该消失。代价是一次 key 查询——所以 `:api-key-fn` 应当便宜或
自己缓存，这一点在请求路径上本来就成立（每个请求都会调它）。

key 查询失败（比如钥匙串没解锁）按不可用处理。这是在画屏幕的路径上，报错应该
属于那个真的去发请求的动作。

**会话当前所在的 provider 即使没有 key 也要出现在候选里**，否则一个停在没配置的
厂商上的会话既看不到自己在哪，也没法离开。

### 4.1 只有配置了多个可用厂商时才带点击线索

候选只有一个时，那一段是纯文本：给一个只有一个选项的菜单加 `mouse-face` 是在
承诺一个不存在的选择。

### 4.2 图形界面用弹出菜单，终端下退回 `completing-read`

用 `display-popup-menus-p` 判定，而不是假设有窗口系统。终端里的 Emacs 是常态，
在那里弹不出菜单不能变成"这个功能不存在"。

### 4.3 鼠标不能是唯一入口

`chat-set-model` 已经存在且必须继续可用。一个只能用鼠标完成的操作，在 Emacs 里
等于没有这个操作。

### 4.4 切换必须走既有的那条路

点击最终调用 `chat-set-model`，不复制它的检查。它已经处理了"请求在飞时不许换"
和持久化——绕过它就是把这两件事漏掉一次。

## Requirement 5: 重画

### 5.1 模型变更后提示符必须重画

`chat-set-model` 今天只重画状态行。提示符一旦带上模型名，它就成了同一个事实的
第二个显示位置，不重画就是留下一个说谎的位置。

### 5.2 重画沿用既有机制，不新增路径

`chat-ui--render-input-prompt` 已经是幂等的（比较已画与该画，一致就不动缓冲区），
并且已经在每次发送时被调用。模型名进提示符后，这个比较自动覆盖它。

## Requirement 6: 行为边界

### 6.1 cmd 模式不显示模型

那一行按回车不会到模型去。显示一个此刻无关的事实，是在训练读者忽略这个位置。

### 6.2 提示符仍然是只读、可自愈的

标记、厂商段、模型名、结束符全都属于提示符：同样带 `chat-ui-prompt` 标记、同样
只读、同样在丢失后由下一次发送重画。新增的 `keymap` 属性必须跟其他属性一样
`rear-nonsticky`，否则输入区会继承鼠标绑定。

## Acceptance

### 标记

1. AI 模式（基线）下提示符含厂商标记与模型名，不含命令名
2. cmd 模式下提示符含 shell 标记与 `cmd`，不含模型名
3. queue 模式下提示符含队列标记与 `queue`
4. 未知 sticky 命令持有输入时，提示符退回只有命令名，不报错
5. 字形不可显示时，提示符降级为纯文本且仍然可用
6. 提示符里不出现 emoji 码位

### 厂商

7. 有已知等价字符的厂商用该字符（Claude、Grok、OpenAI、Gemini 各一条）
8. 其余厂商用显示名首字母大写
9. provider 查不到配置时用通用星标
10. 已知品牌色的厂商，其标记 face 在明暗背景下各有一个前景色
11. 品牌色 face 不被 chat.el 的任何非厂商元素引用

### 模型名

12. 显示的模型名等于 `(plist-get config :model)`
13. 超过配置宽度的模型名被截断，且 `help-echo` 含完整值
14. 宽度用 `string-width` 计算（CJK 模型名不被算成一半）

### 点击

14a. 候选只含配置过的厂商，没有 key 的注册项不出现
14b. key 在会话中途出现或消失，下一次显示即反映
14c. key 查询报错的厂商按不可用处理，且不影响提示符绘制
14d. 会话当前的 provider 即使没有 key 也在候选中，且不重复出现
15. 候选多于一个时，厂商段带 `keymap` 与 `mouse-face`
16. 候选只有一个（或没有）时，厂商段不带 `keymap` 也不带 `mouse-face`
17. 弹不出菜单的环境下走 `completing-read`
18. 切换调用 `chat-set-model`，不绕过它的检查
19. 请求在飞时点击切换被拒绝（由 4.4 继承而来，须有用例）

### 重画与边界

20. `chat-set-model` 之后提示符里的模型名已更新
21. 提示符与已画内容一致时不改动缓冲区（幂等，沿用现有断言）
22. 提示符整体只读，含新增的标记与厂商段
23. 输入区不继承提示符的 `keymap`
24. 提示符被删除后，下一次发送重画出的仍是完整提示符（标记与厂商段都在）

## Notes

模块划分：标记表放 `lisp/ui/chat-mark.el`，是纯函数——厂商符号进，字形与 face
出，不碰缓冲区、不读会话。提示符组合留在 `chat-ui.el`（它已经在那里）。点击命令
放 `chat-ui.el`，因为它要读会话、要调 `chat-set-model`。

放在 `lisp/ui/` 而不是 `lisp/core/`：标记是显示层的事，没有任何 core 模块需要
知道 Claude 长什么样。这与 spec 005 把 `chat-markdown.el` 放进 core 的判断不
冲突——那个模块要被 `chat-transcript.el` 这样的 core 模块用到，这个不会。

图标思路参考同平台的 termini-desktop：单色标记 + 品牌色描边、有工具就显示工具
标记、没有才显示通用星标、shell 单独一个标记。它用的是 SF Symbol 和打包的 PNG，
我们用不了；能搬的是判断方式，不是素材。
