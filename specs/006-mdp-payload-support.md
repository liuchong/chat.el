# 006: MDP Payload Support Spec

## Overview

**MDP 是数据传输协议，地位类似 JSON，不是文档工具。** 这一句决定了这份 spec 的
全部结构，所以放在最前面。它替换的是载荷层——今天由 JSON 占着的那个位置——
而不是替换 Markdown，也不与 Markdown 争文档格式的位置。

它恰好用 Markdown 的语法写成：只解析三类构造（两级 ATX 标题、`- key: value`
键值列表、GFM 管道表格），其余一切（段落、强调、引用、`###` 及以下标题、
围栏代码块）一律是注释，对解析结果零影响。**可读性和可展示性是它的性质，
不是它的用途。** JSON 也能被格式化打印，但没人因此说 JSON 是文档格式。

这份 spec 回答两个问题：chat.el 该不该支持它、支持在哪；以及 `chat-mdp.el`
这个模块的定位到底是什么。

第一个问题的结论是**部分采纳**：MDP 的核心价值对 chat.el 恰好成立，但它并不解决
我们最痛的那个问题，所以采纳范围要划清，不能因为协议是自家的就整体套上去。

第二个问题的结论是**它首先是编解码器**：把 MDP 报文与 Elisp 内部表示互相转换。
显示只是它的次要职责，而且要跟 spec 005 划清界限——详见 Requirement 4。

## Why It Fits Here

MDP 的核心设计是"一份文本，两种读法"：机器只读白名单标记，人和 AI 读全部内容。

chat.el 的会话记录恰好就是这种双读场景。同一段文本要同时满足：

1. 程序要能稳定解析出结构（工具调用、工具结果）
2. 人要能在缓冲区里读懂它
3. 模型下一轮还要再读一遍它

今天这三件事是分开凑的：程序读 JSON，人看被截断的 JSON，模型读同一段 JSON。
JSON 对第一条勉强够用，对第二三条是负担。

还有一个现成的便利：spec 005 的 Markdown 展现引擎一旦落地，**MDP 报文的文档视图是
免费的**。它本来就是合法 Markdown，键值列表显示成列表，表格显示成对齐的表格。
这是 MDP 相对任何自定义格式的结构性优势——换成自定义语法，显示逻辑就得从零写。

## The Real Pain, And Whether MDP Solves It

必须先说清楚这一点，否则后面的采纳范围没有依据。

**今天的痛点有证据。** `chat-tool-caller--fix-broken-json`
（`lisp/tools/chat-tool-caller.el:311`）是一串经验性的修补：剥掉开头多出来的
`json` 字样、剥掉围栏、把 `"_call"` 改回 `"function_call"`、把 `"_execute"` 改回
`"shell_execute"`。一个协议需要这种函数，说明协议在模型手里不稳。

**MDP 解决其中一半。** 模型在结构周围写解释文字，是 JSON 协议下的破坏性行为——
文本挤在 JSON 外面，解析器只能靠"找围栏""剥前缀"去猜边界。MDP 把这件事写进了
规范：注释不是容错，是定义。§7 的原话是，白名单之外的任何 Markdown 文本都不是
错误，"MDP 不存在语法错误的第三种状态"。模型爱写解释这个改不掉的习惯，在 MDP 下
从故障源变成了特性。

**MDP 不解决另一半。** 最容易出错的参数是多行的：文件内容、补丁、代码。查 §5.2，
MDP 的值是单行的，多行字符串要写成带 `\n` 转义的引号串——**和 JSON 一样的转义
问题**。所以在最痛的那类参数上，MDP 没有优势。

这不是 MDP 的缺陷，是它的定位：它是载荷层协议，不是大块文本的容器。而 chat.el
对这一半**已经有更好的答案**：`*** Begin Patch` / `*** End Patch` 这种哨兵块，
内容原样、零转义。哨兵块在这件事上比 JSON 和 MDP 都强，应当保留。

结论：MDP 用在它强的地方（有结构、值是标量、要被人和模型同时读），不动它不强的
地方（大块原文）。

## Goals

1. MDP 报文与 Elisp 内部表示可双向无损转换。这是模块存在的首要理由
2. 工具调用的文本协议可以用 MDP 表达，模型在报文周围写的解释不再造成解析失败
3. 工具结果回灌给模型时是结构化的，同时在缓冲区里人能直接读
4. 文档视图复用 spec 005，不写第二套文档渲染器；机器视图由本模块提供，
   因为它是 005 结构上做不到的那一半
5. `chat-mdp.el` 独立可用：不依赖 mdp 仓库的实现，也不硬依赖 spec 005
6. chat.el 自带解析与发射，规范变动只牵动这一个模块

## Non-Goals

1. 不替换原生 function calling。provider API 的线上格式是 JSON，那是 API 定的，
   不是我们能选的
2. 不替换 `*** Begin Patch` 哨兵块。见上一节：多行原文用哨兵块更好
3. 不替换会话持久化的 JSONL。那是纯机器读的记录，没有人在读，换格式买不到东西，
   还要拿已有记录的兼容性去赌
4. 不做第二套文档渲染器。MDP 的白名单是 Markdown 的子集，文档视图归 spec 005；
   本模块的显示职责严格限定在 Requirement 4 划的那条线以内
5. 本期不实现 MDS 校验层。判断和触发条件见 Markdown Schema 一节
6. 不追求一致性测试集全绿。按 chat.el 实际用到的子集实现，未用到的构造宁可明确
   报不支持，也不做半套

## Adoption Scope

按"MDP 强不强"逐项判定，不整体套用。

| 位置 | 现状 | 判定 | 依据 |
| --- | --- | --- | --- |
| 文本式工具调用 | `{"function_call": ...}` + 一串修补 | **采纳** | 注释规则消掉"模型爱解释"这个故障源 |
| 工具结果回灌 | 截断的纯文本 | **采纳** | 双读场景，MDP 的正命题 |
| 大块文本参数（补丁、文件内容） | `*** Begin Patch` 哨兵块 | **保留现状** | MDP 单行值 + 转义，不如哨兵块 |
| 原生 function calling | provider 的 JSON | **不动** | 格式不由我们决定 |
| 会话持久化 | JSONL | **不动** | 纯机器读，换了不买到东西 |
| 文档视图 | 无 | **免费** | MDP 是合法 Markdown，spec 005 直接渲染 |
| 机器视图 | 无 | **本模块自建** | 需要解析结果，005 拿不到 |
| MDS 校验 | 无 | **本期不做** | 规范是草案且明确可分层，推迟零代价 |

## Status: Codec And Views Implemented, Prompt Flip Held

已落地：Requirement 1（编解码器，`lisp/core/chat-mdp.el`）、Requirement 4
（两个视图，机器视图与 `chat-mdp-annotate`）、Requirement 2.1 的**解析侧**
（`chat-tool-caller-parse` 先试 MDP 再试 JSON，命中格式记在
`chat-tool-caller-format-counts`）。2.2 守住了：修补函数没有进 MDP 路径。

**未落地，且是有意的：2.1 的提示词侧与 Requirement 3。** 理由用的是这份 spec
自己的那条——"凭感觉收掉分支就是拿可用性赌"。同一条逻辑反过来同样成立：凭感觉
**换掉**提示词要求的格式，也是拿可用性赌。这两件事都改变模型实际写出什么，而
本次施工没有对真实模型的验证条件。

现在的状态恰好是取证状态：双向接受已经开了，格式命中计数已经在记。等到计数里
有真实分布，再决定提示词要不要换、JSON 分支要不要收。

一个必须说清的危险，因为它不是"少一个功能"而是"多一种错法"：MDP 报文解析成功
但语义错了（模型写了 `- name: shell_execute` 却把命令写成散文），会得到一个
参数为空的调用。JSON 路径没有这个错法，因为参数缺失时 JSON 通常整体解析失败。
审批层挡住了大部分后果，但这条要写进未来那次提示词切换的验收里，不能等切换完
再想起来。

## Requirement 1: A Codec

模块首先是一个编解码器。这是它的定位，也是它唯一不可替代的职责：显示这件事
spec 005 能做大半，把 MDP 报文变成 Elisp 数据只有它能做。

### 1.1 独立模块

新模块 `lisp/core/chat-mdp.el`，两个入口：

```
chat-mdp-parse  (text) → value | (error . code . line)
chat-mdp-encode (value) → text
```

- MUST NOT 依赖 mdp 仓库的 Rust 实现或任何外部进程。按 SPEC.md 实现规范，
  不链接实现
- MUST NOT require `lisp/ui/` 下的任何模块。本仓库的依赖方向是严格的
  ui → core（可核实：`lisp/core/` 里没有一处 require `chat-ui`），
  一个协议模块去依赖显示模块会把它倒过来
- MUST NOT 硬依赖 `chat-markdown.el`。它在没有显示层的场景下要能单独用：
  批处理、测试、别处调用编解码器
- 解析按 §6 的参考流程：单遍逐行扫描 + 缩进栈。先整体跳过围栏代码块，
  再识别 ATX 标题、键值列表、管道表格，其余一切是注释
- 发射按 §8 的规范序列化形式，保证字节级稳定

### 1.2 Elisp 内部表示

内部表示要选定并写死，因为它是所有调用方看到的那个面：

- 对象 → alist，键为字符串，MUST 保留文档出现顺序（§3.1 的 SHOULD 在我们这里
  收紧为 MUST：工具调用的参数顺序影响可读性，而乱序的报文没法逐字比对测试）
- 数组 → list
- 字符串 → string；number → number；boolean → `t` / `:false`；null → `:null`
- `t` / `:false` / `:null` 这套区分是必须的：Elisp 里 `nil` 同时是假、空表和
  空值，而 MDP 的 `false`、`[]`、`null` 是三个不同的值。用 `nil` 表示其中任何
  一个，encode 回去就分不出该写哪个，往返就不是无损的
- 空对象 `{}` → `:empty-object`。同理：空 alist 也是 `nil`

### 1.3 往返无损

`encode` 后 `parse` MUST 得到相同的值。这是编解码器的定义，也是选定上面那套
表示的验收依据——任何一处用 `nil` 兼表两义，都会在这条上暴露。

注意方向：无损的是**值**的往返，不是**文本**的往返。注释在 parse 时按规范被丢弃，
encode 不可能把它们变回来。要保留原文的场景保留原文，不要指望 encode 复原。

### 1.4 必须实现的白名单

- 一级、二级 ATX 标题（§4.1）。`###` 及以下是注释
- 键值字段与嵌套容器（§4.2），按缩进层级嵌套
- GFM 管道表格（§4.3）
- 序言区（§4.4）
- 类型推导按 §5.1 的优先级：引号串 → number → boolean → null → `{}` → `[]` →
  string 原文
- 引号串转义按 §5.2 的五条，其余 `\x` 原样保留

### 1.5 必须实现的注释规则

这是采纳 MDP 的主要理由，所以它是硬要求而不是尽力而为：

- 白名单之外的一切 MUST 被跳过且对结果零影响：段落、空行、`###` 及以下标题、
  引用块、图片、链接、行内代码、强调、有序列表、不匹配键值文法的 `-` 列表项、
  setext 标题、水平线、HTML 注释与 HTML 块
- 围栏代码块 MUST 整体跳过，**即使块内含白名单语法**。这一条必须有专门的测试：
  它决定了模型能否安全地在报文里贴一段示例
- 注释行与空行穿插在嵌套结构中间 MUST NOT 打断结构

### 1.6 错误码

§7 的八个错误码（MDP-E001 到 E009）MUST 各自可被检出，且 MUST 带行号。
理由是可诊断性：一个报文被拒时，我们要能告诉模型它错在第几行第几条，
而不是"解析失败"。

## Requirement 2: Tool Calls In MDP

### 2.1 双向接受

过渡期 MUST 同时接受 JSON 和 MDP 两种工具调用报文。理由不是兼容包袱，
而是模型分布：不同模型对提示词的服从度不同，单向切换会让一部分模型全面失效。

- 提示词要求 MDP
- 解析先试 MDP，不成再试 JSON
- 记录哪种格式命中了，这是后续决定能否收掉 JSON 分支的依据。凭感觉收掉分支
  就是拿可用性赌

### 2.2 修补函数的去向

`chat-tool-caller--fix-broken-json`（`lisp/tools/chat-tool-caller.el:311`）
MUST NOT 被搬进 MDP 路径。它存在的理由是 JSON 协议撑不住模型的输出习惯；
把同一堆经验性修补复制到新协议上，等于把旧协议的病一起搬过来。MDP 路径的
容错只能来自规范里写着的注释规则。

### 2.3 大块参数仍走哨兵块

一次工具调用里，标量参数用 MDP 键值字段，多行原文参数用 `*** Begin Patch`
风格的哨兵块。由于围栏与哨兵块内容在 MDP 里都是注释，二者在同一份报文里共存
不冲突——这正好是 §6 那条"围栏整体跳过"规则的用处。

## Requirement 3: Tool Results In MDP

结构化的工具结果（文件列表、搜索命中、诊断项、状态表）用 MDP 回灌：

- 机器视角：下一轮请求拿到的是结构，不是要再解析一次的纯文本
- 人的视角：同一段文本在缓冲区里就是渲染好的列表和表格
- 结果里的自由文字（说明、告警、约束）作为注释同文共存，不影响解析

这是 MDP 的正命题在我们这里最直接的落地：一份文本，两种读法，不做两份。

## Requirement 4: Two Views, Two Owners

先前的版本在这里写错了：它要求"MDP 报文 MUST NOT 有自己的显示逻辑，一律交给
spec 005"。那条规则会让 `lisp/core/chat-mdp.el` 依赖 `lisp/core/chat-markdown.el`
才能显示任何东西，把一个协议模块的可用性绑在显示层上；一旦渲染器不在，
编解码器就成了瞎子。方向也别扭：协议不该向显示要能力。

正确的划法来自 MDP 自己的正命题——**一份文本，两种读法**。既然是两种读法，
就是两个视图，各有其主：

### 4.1 文档视图（人的读法）归 spec 005

MDP 报文是合法 Markdown，所以 005 的渲染器直接就能显示它：键值字段成列表、
表格对齐、`###` 注释标题和强调照常渲染。

`chat-mdp.el` MUST NOT 与它竞争。具体地，本模块 MUST NOT 做：隐藏语法标记、
代码块语法高亮、列表符号替换、链接折叠。这些是 005 的职责，做第二份就是
"同样的东西两份实现，一定分叉"——那正是 005 存在的理由。**005 在场时，
文档视图一律由它渲染。**

### 4.2 机器视图（机器的读法）归 chat-mdp.el

这一半 005 结构上做不到，因为它没有解析结果：它只看见 Markdown 语法，
不知道哪一行是结构、哪一行是注释，也不知道 `- age: 28` 的值是数字 28 而不是
字符串。`chat-mdp.el` 知道，因为它刚刚解析完。

所以机器视图**从解析出的 Elisp 值渲染**，不是从 Markdown 文本重新渲染。
它展示的是解析器实际提取到了什么。

这不是可有可无的调试功能，它是 MDP 那句"一份文本两种读法"能否被验证的前提：
两种读法是否一致，看不见机器视图就无从判断。一个报文人看着没问题而程序读出来
少了一个字段，除了把机器视图摆出来，没有别的办法发现。

### 4.3 独立时的有限渲染

`chat-markdown.el` 不在场时，`chat-mdp.el` MAY 做有限的美化，范围写死：

- 区分结构与注释（结构正常显示，注释淡化）
- 表格按显示宽度对齐

仅此两项。理由是它们各自都不是文档渲染的复制品：前者只有拿到解析结果才做得到，
后者是共享的同一份实现（见 4.4）。

不做的部分靠 MDP 自己兜底：它的 §1 明确说了优雅降级——不支持 GFM 表格的渲染器
里，表格退化成普通文本行，数据仍然肉眼可读。所以"没有渲染器"的落地行为是
纯文本，那是可接受的，不需要我们补一个半套的文档渲染器去填。

### 4.4 对齐只有一份实现

表格按显示宽度对齐，文档视图和机器视图都要。它 MUST 是 spec 005 §5.1.1 里那个
独立的纯函数，两边 require 同一个，MUST NOT 各写一份。

一个中文表格在文档视图里对齐、在机器视图里错位，比两边都不对齐更难查。

## Markdown Schema (MDS)

MDP 配套还有一个 MDS（`SCHEMA.md`）：**MDP : MDS = JSON : JSON Schema**。
一份 MDS 模式文档描述"一份 MDP 数据文档应该长什么样"，校验器据此验证段落结构、
字段存在性、类型与取值约束。它自举——模式文档本身就是合法的 MDP 文档，
零新语法，只用标题、键值、表格这三类白名单构造。

### 判定：本期不做，而且推迟是零代价的

推迟不需要理由，除非推迟有代价。这里没有代价，依据是 MDS 规范自己写的分层：
"MDP 核心解析器不感知 MDS 的存在；校验是解析之上的独立一层，可只用其一"。
所以它不是"以后再补的功能"，而是**规范设计上就可以后加而不动解析器**。
Requirement 1 那个编解码器不会因为将来加校验而改一行。

在这个前提下，本期不做的三条依据：

1. **它是草案，且明确允许破坏性变更。** `SCHEMA.md` 标 `MDS/0.1`、状态"草案"，
   写着"0.x 期间允许破坏性变更"。而 MDP 至少自称稳定。跟着一个允许破坏性变更的
   规范写校验器，就是给自己排一串返工
2. **我们已经有一份 schema 了。** 工具注册表里的参数声明就是
   （`:name "command" :type "string" :required t`，见 `chat-tool-forge`）。
   现在引入 MDS，等于同一件事有两种表达方式，而两份 schema 必然分叉——
   这跟 spec 005 反对两个渲染器是同一条理由
3. **顺序上它排在验证之后。** MDP 报文路径在工具调用上能不能站住，要靠
   Requirement 2.1 的命中率数据说话。在载荷层还没被证明之前先做校验层，
   是给一个可能要撤的决定加固

### 什么情况下这个判断会翻转

写下来，这样将来不必重新推一遍：

- MDS 出草案（不再允许破坏性变更），并且
- MDP 报文在工具调用路径上的命中率数据证明它站得住，并且
- 有一个 MDS 能做而现在做不到的具体用途

第三条已经有一个像样的候选，值得先记下来：**从工具注册表发射 MDS**，
让模型收到的 schema 和它要写的载荷用同一种语法。今天提示词是用散文加一段 JSON
形状去描述工具的；如果载荷是 MDP 而 schema 是 MDS，两者同语法，模型不必在两套
语法之间切换。这是把"一份文本两种读法"用到 schema 自己身上。

注意方向：这个用途的价值在**发射**（我们的注册表 → MDS 给模型看），
不在**校验**（模型的报文 → 我们验）。校验这一侧我们已经在做参数检查了。
所以真要动手时，先做 emitter，不要一上来就做 validator。

### 现在就要守住的一条

Requirement 1.4 的类型推导 MUST 只做 MDP §5 的四种线类型
（number / boolean / null / string），MUST NOT 顺手去猜日期、枚举、金额。
一切语义类型按规范归 MDS 层。

这条现在就要守，因为它是**将来能不动解析器就加上 MDS 的前提**。解析器里一旦
掺进猜测式推导，MDS 那层就会和它打架：数据文档里 `2026-07-21` 该是字符串还是
日期，得由模式文档说，不由解析器猜。

## Dependency And Risk

必须写下来，因为这是引入一个外部规范的代价：

- **规范尚新。** mdp 仓库 `SPEC.md` 标 v0.0.1，同一处又写"正式版（Stable）·
  规范标识 MDP/1.0"。两者对稳定性的暗示不一致。采纳前需要确认版本语义，
  否则我们会跟着一个还在动的规范改解析器
- **缓解办法是方向依赖。** chat.el 实现规范，不依赖实现，也不被 mdp 仓库依赖。
  规范变了我们改自己的解析器，不会牵动别的东西
- **双向接受期是安全阀。** 在有数据说明 MDP 路径命中率足够高之前，
  不收掉 JSON 分支

## Acceptance

### 解析

- [ ] §9 的四个完整示例（平铺、嵌套及各自的解析结果）逐字通过
- [ ] 键值容器嵌套到三层以上，缩进栈正确
- [ ] 类型推导按 §5.1 优先级：`001` 是字符串、`True` 是字符串、
      `{}` 是空对象、`"{}"` 是字符串、未闭合引号是字符串原文
- [ ] §5.2 的五个转义正确，其余 `\x` 原样保留
- [ ] 单列表格解析为标量数组，多列表格解析为行对象数组

### 注释规则

- [ ] 报文前后左右加任意段落、强调、引用块，解析结果逐字不变
- [ ] 围栏代码块里写一段完整的 MDP 报文，外层解析结果不受任何影响
- [ ] `###` 及以下标题不进结构，且不打断所属段落的自有内容
- [ ] 注释行与空行插在嵌套容器中间，不打断嵌套

### 错误码

- [ ] 八个错误码各有一个用例，各自报出正确的码与行号
- [ ] 白名单外的任意 Markdown 文本 MUST NOT 报错（不存在第三种状态）

### 内部表示与往返

- [ ] 对象是键为字符串的 alist，且键序与文档出现顺序一致
- [ ] `false`、`[]`、`null`、`{}` 解析出四个互不相等的值，都不是 `nil`
- [ ] 上面四个值各自 `encode` 回去，写出的仍是 `false` / `[]` / `null` / `{}`，
      没有一个被写成另一个
- [ ] `encode` 后 `parse` 得到相同的值（值的往返无损）
- [ ] 带注释的报文 `parse` 后 `encode`，注释消失且不报错——无损的是值不是文本，
      这条钉住这个预期，避免把它当缺陷去修
- [ ] 输出符合 §8 规范形式：LF、两空格缩进、`| cell |` 单空格填充、
      块间空行、字符串只在有歧义时加引号

### 类型分层

- [ ] `2026-07-21` 解析为字符串，不是日期。解析器不做语义推导，
      这是将来能不动它就加上 MDS 的前提

### 工具调用

- [ ] 模型发 MDP 工具调用能被执行
- [ ] 模型在报文前后写解释文字，仍能被执行（当前 JSON 路径下会失败）
- [ ] 模型发旧式 JSON 工具调用仍能被执行
- [ ] MDP 路径上没有等价于 `--fix-broken-json` 的经验性修补
- [ ] 同一份报文里标量参数走 MDP、多行参数走哨兵块，两者都取到正确的值

### 工具结果

- [ ] 结构化结果以 MDP 回灌，下一轮请求里是结构而不是待解析的文本
- [ ] 同一段结果在缓冲区里显示为对齐的表格或列表

### 两个视图

- [ ] `chat-markdown.el` 在场时，MDP 报文的文档视图由它渲染，
      `chat-mdp.el` 不参与
- [ ] `chat-mdp.el` 里没有隐藏语法标记、代码块语法高亮、列表符号替换、
      链接折叠这四类逻辑（静态断言，防止长出第二个文档渲染器）
- [ ] 机器视图从解析出的值渲染，不是从 Markdown 文本重新解析
- [ ] 一个报文人看着有某字段而解析器没取到，机器视图能看出这个差
- [ ] 含中文单元格的表格，在文档视图和机器视图里对齐结果相同
      （同一份对齐实现）
- [ ] 对齐函数只有一处定义，两边都 require 它

### 模块独立性

- [ ] 只 `require 'chat-mdp`（不加载 `chat-markdown`、不加载任何 ui 模块），
      parse 和 encode 全部可用
- [ ] `chat-mdp.el` 不 require `lisp/ui/` 下任何模块（静态断言）
- [ ] `chat-markdown.el` 缺席时，有限渲染仍可用，且只做区分结构与注释、
      表格对齐这两项

### 边界

- [ ] 不依赖 mdp 仓库的实现，不起子进程
- [ ] 会话持久化仍是 JSONL，未被本 spec 改动
- [ ] 原生 function calling 路径未被本 spec 改动
- [ ] 本期没有 MDS 校验代码，且解析器里没有任何为 MDS 预留的钩子——
      规范说了校验是独立一层，预留钩子等于提前承担耦合

## Behavior Boundaries

- **MDP 是数据传输协议，不是文档工具。** 它占的是 JSON 的位置，不是 Markdown 的
  位置。它的可读性是性质而非用途——JSON 也能格式化打印，没人因此说 JSON 是文档
  格式
- **MDP 是载荷格式，不是交互协议。** 它替换 JSON 的位置，不定义请求响应模式、
  不定义生命周期。我们的 agent 循环、审批、上下文管理都不因它改变
- **`chat-mdp.el` 首先是编解码器。** 它不可替代的职责是 MDP 与 Elisp 内部表示
  的互转。显示是次要职责，而且被 Requirement 4 划死了范围
- **文档视图归 005，机器视图归本模块。** 前者是 Markdown 语法的渲染，MDP 报文
  免费获得；后者需要解析结果，005 结构上拿不到。两者不重叠，也不许重叠
- **本模块不长成第二个文档渲染器。** 隐藏标记、代码高亮、符号替换、链接折叠
  一概不做。005 缺席时的落地行为是纯文本加两项有限美化——MDP 本就设计为优雅
  降级，纯文本是可接受的结果
- **大块原文不进 MDP。** 补丁和文件内容继续走哨兵块。MDP 的值是单行的，
  多行要转义，在这件事上它没有优势
- **JSON 不是要被清掉的技术债。** 原生 function calling 和会话持久化里的 JSON
  各有其正当理由，本 spec 不碰
- **注释规则是采纳的理由，也是唯一的容错来源。** MDP 路径不接受任何规范之外的
  经验性修补；撑不住就说明报文不合规，该报错码和行号，不该猜
- **MDS 本期不做，且不预留钩子。** 语义类型归 MDS 层，解析器只做四种线类型。
  规范明说校验是解析之上的独立一层，所以推迟是零代价的；预留钩子反而是提前
  承担耦合。翻转条件写在 Markdown Schema 一节里
